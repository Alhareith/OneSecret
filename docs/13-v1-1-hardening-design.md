# V1.1 — التحصين التشغيلي: التقرير النهائي

**الحالة:** مكتملة ومتحقق منها في بيئة اختبار معزولة في 27 أغسطس 2026. لا تضيف هذه النسخة حسابات أو صورًا أو تغييرًا في نموذج AES-256-GCM؛ هدفها أن تجعل الاستعمال العام أصعب على التخمين والإغراق، وأقل عرضة لتخزين المحتوى الحساس في المتصفح.

## المشكلة بلغة بسيطة

الرابط العشوائي وSecret Code لا يكفيان وحدهما أمام من يكرر المحاولات بسرعة. يمكن لشخص أن يرسل آلاف طلبات الإنشاء، أو يحاول فتح معرّفات كثيرة، أو يخمّن Secret Code. الحل المختار هنا هو **محدد الطلبات**: عدّاد زمني يقول للمصدر الذي يرسل طلبات كثيرة «انتظر قليلًا»، ثم يعيد استجابة عامة `429 Too Many Requests`.

> هذا ليس تشفيرًا جديدًا ولا يمنع تصوير الشاشة. هو حارس عند باب API يقلل الإساءة الشائعة، ويبقي الوظيفة الطبيعية كما هي.

## ما نُفذ

| المجال | التنفيذ الفعلي | أثره على المستخدم العادي |
|---|---|---|
| إنشاء الرابط | حتى **6** محاولات خلال **10 دقائق** لكل مصدر اتصال | لا يتأثر الاستخدام الطبيعي لإنشاء رسالة أو عدة رسائل قليلة |
| كشف الرابط | حتى **60** طلب Reveal خلال **دقيقة واحدة** لكل مصدر | يبقى فتح الرسالة عدة مرات قبل الانتهاء ممكنًا ضمن سلوك V1 |
| Secret Code الخاطئ | حتى **5** محاولات خاطئة خلال **10 دقائق** لكل مصدر ولكل رسالة | يتوقف التخمين مؤقتًا؛ الكود الصحيح لا يضيف محاولة فاشلة |
| رد الحظر | `429` مع `Retry-After` ورسالة عامة | لا يَكشف وجود السر أو صحة الكود أو تفاصيل سياسة الحماية |
| سجل الحماية | حدث مختصر عند الحظر فقط: نوع العملية والنتيجة | لا يسجل النص أو Secret Code أو `secret_id` أو الرابط |
| سجل الوصول | صورة التشغيل تشغّل Uvicorn مع `--no-access-log` | لا يطبع خادم التطبيق مسار `/s/{id}` تلقائيًا في stdout |

يطبق المحدد **نافذة زمنية متحركة**: يحتفظ فقط بأوقات الطلبات داخل الفترة المناسبة، ثم يزيل الوقت القديم قبل اتخاذ القرار التالي. مفاتيح الذاكرة هي بصمات HMAC من نطاق العملية ومصدر الاتصال، وليست IP أو `secret_id` كنص ظاهر. كما تنظف المفاتيح التي تجاوزت أطول نافذة مرة كل دقيقة على الأكثر؛ لذلك لا تبقى مفاتيح مصادر قديمة إلى ما لا نهاية.

## تفاصيل Secret Code المهمة

لا يُخصم من حد Secret Code إلا بعد أن يقرر منطق الخدمة أن الكود المرسل غير صحيح أو أن كودًا مطلوبًا لم ينجح. قبل التحقق، يفحص الخادم هل الرابط في فترة انتظار سابقة؛ لذلك لا يستهلك الشخص محاولات جديدة عندما يكون محظورًا أصلًا. أما طلب Reveal العام فله حد مستقل أولًا لحماية المعرفات نفسها.

هذا الفصل مهم: رسالة محمية لا تسمح لمحاولات خاطئة على رابط واحد بأن تمنع رابطًا محميًا آخر. وفي الواجهة، لا يقال للمستخدم إن الكود «خاطئ» عند `429`؛ تظهر رسالة انتظار عامة فقط. كذلك تميز صفحة الإنشاء وصفحة الكشف التلقائي الحظر المؤقت عن الرابط غير المتاح.

## رؤوس حماية المتصفح

تضاف الرؤوس التالية إلى كل استجابة من التطبيق، ثم تضاف رؤوس منع التخزين إلى الاستجابات التي تتعامل مع رابط سر محدد.

| الرأس | أين يطبق | القرار ولماذا |
|---|---|---|
| `X-Content-Type-Options: nosniff` | جميع الردود | يمنع المتصفح من تخمين نوع المحتوى بدل احترام النوع المعلن |
| `X-Frame-Options: DENY` | جميع الردود | يمنع تضمين الصفحة داخل إطار |
| `Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'` | جميع الردود | يمنع الإطارات ويقيد تغيير base URL، من دون فرض `default-src` قد يكسر الخطوط الحالية |
| `Referrer-Policy: no-referrer` | جميع الردود | لا يمرر المتصفح رابط السر كـReferrer عند الانتقال لخارج الصفحة |
| `Permissions-Policy` | جميع الردود | يعطل الكاميرا والموقع والمايكروفون والدفع وUSB، مع الإبقاء المقصود على `web-share=(self)` لمشاركة الهاتف الأصلية |
| `Cache-Control: no-store` مع `Pragma: no-cache` و`Expires: 0` | `/s/{id}`، وحالة الرابط، وكل نتائج Reveal بما فيها `200` و`401` و`410` و`429` | يطلب من المتصفح والوسطاء عدم تخزين النص أو بيانات الرابط الحساسة |

تبقى الصفحة الرئيسية وملفات JavaScript/CSS الثابتة قابلة للتخزين المؤقت؛ فهي لا تتضمن سرًا، وهذا يحافظ على سرعة فتح الموقع. كما أن عدم إضافة `default-src` إلى CSP قرار مقصود: سياسة مصادر صارمة تحتاج مراجعة موارد الخط قبل اعتمادها، ولا تُضاف لمجرد زيادة عدد الرؤوس.

| سجل التشغيل | تأكد عدم وجود الرابط أو Secret Code الاختباري في سجل التطبيق؛ ظهر فقط حدث الحظر المجرد |

## حدود معروفة وقرار التشغيل

محدد الطلبات في الذاكرة مناسب لهذه المرحلة، لكنه **لكل عملية FastAPI فقط**. إعادة تشغيل الخادم تصفره، وتشغيل أكثر من نسخة يجعل لكل نسخة عدادها المستقل. عند الحاجة إلى حد موحد بين النسخ يكون الحل المرحلة التشغيلية التالية هو مخزن مركزي مثل Redis، مع تصميم ومراقبة مستقلين؛ لا نضيفه الآن بلا حاجة مثبتة.

يعتمد المصدر على `request.client.host` كما يراه الخادم، ولا يثق بـ`X-Forwarded-For` لأن العميل يستطيع تزويره إن لم يضبط proxy موثوق. قبل النشر خلف proxy يجب التحقق من أن التطبيق يرى عنوان العميل الصحيح؛ إن ظهر عنوان proxy واحد لكل المستخدمين، فقد يتشاركون الحد. لا تُفعّل الثقة برؤوس forwarded عشوائيًا؛ تضبط فقط في طبقة proxy موثوقة ومحددة.

أيضًا، تحقق FastAPI من صحة جسم إنشاء الرسالة يحدث قبل دخول دالة endpoint، لذلك الطلبات غير الصالحة بنيويًا لا تُحسب حاليًا ضمن حد الإنشاء. هذا قرار موثق لهذه المرحلة لتجنب تغيير ترتيب التحقق أو كشف تفاصيل الأخطاء. وإذا ظهرت إساءة فعلية بطلبات تالفة كثيرة، تُعالج أولًا عند طبقة الحافة أو proxy، لا بإضعاف رسائل أخطاء API الآمنة.

تعطيل سجل Uvicorn لا يتحكم في سجلات CDN أو موازن الحمل أو proxy خارجي. عند النشر، يبقى على المشغل التأكد من سياسة تنقيح مسارات روابط الأسرار في تلك الطبقة. ولا تغيّر V1.1 نموذج الثقة: الخادم ما زال يرى النص لحظة التشفير وفك التشفير، والموقع لا يستطيع منع النسخ أو تصوير الشاشة بعد العرض.

## ما يلي بعد V1.1

المرحلة المعتمدة التالية هي **V1.2: إلغاء الرابط من المرسل**. لا تبدأ الصور قبل V1.2؛ فهي نطاق V1.3 مستقل ومحدد، وليست جزءًا من التحصين الحالي.
