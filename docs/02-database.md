# المرحلة 2: قاعدة البيانات ونموذج السر

## الهدف

إنشاء شكل منظم للسجل الذي يمثل السر في قاعدة البيانات. هذه المرحلة لا تشفّر الرسائل ولا تنشئ روابط ولا تعرض أي صفحة للمستخدم؛ هي فقط تجهز المكان الذي سيُحفظ فيه النص المشفّر لاحقًا.

## الفكرة الأساسية

قاعدة البيانات تحفظ **الرسالة المشفّرة** فقط، ولا تحفظ الرسالة الأصلية. كما لا تحفظ مفتاح التشفير. عندما نصل لمرحلة التشفير، Python سيحوّل النص إلى ciphertext ثم يحفظ هذا الناتج في الجدول.

### مصطلحات مهمة

| المصطلح | معناه بالبلدي | لماذا نحتاجه؟ |
|---|---|---|
| `ciphertext` | النص بعد تشفيره، أي يصبح غير مفهوم | حتى لا يكون السر ظاهرًا في قاعدة البيانات |
| `nonce` | قيمة عشوائية جديدة تستخدم مع التشفير | تجعل كل عملية تشفير مختلفة وآمنة عند تنفيذ AES-GCM لاحقًا |
| `created_at` | وقت إنشاء السر | لمعرفة وقت بداية دورة حياة السر |
| `expires_at` | وقت انتهاء السر | لمنع الوصول بعد المدة المحددة |
| `used_at` | وقت قراءة السر لأول مرة | لمنع القراءة الثانية |

## جدول `secrets`

| الحقل | النوع | الغرض |
|---|---|---|
| `id` | نص عشوائي قصير | هو معرف الرابط، وليس رقمًا متسلسلًا |
| `ciphertext` | نص طويل | يحتفظ بالنص المشفّر فقط |
| `nonce` | نص قصير | يحتفظ بقيمة nonce الخاصة بالرسالة |
| `created_at` | وقت وتاريخ | وقت إنشاء السجل بالـUTC |
| `expires_at` | وقت وتاريخ | آخر وقت يسمح فيه بالقراءة |
| `used_at` | وقت وتاريخ أو فارغ | يصبح له قيمة بعد Reveal الناجح |

## لماذا لا يوجد حقل اسمه `status`؟

نستطيع معرفة الحالة من الحقول الموجودة بدل تخزينها مرتين. إذا كان `used_at` غير فارغ فالسر مستخدم. وإذا كان الوقت الحالي بعد `expires_at` فالسر منتهٍ. وإذا كان `used_at` فارغًا ولم ينته الوقت فالسر فعال.

هذا أبسط وأنظف؛ لأن تخزين الحالة في عمود منفصل قد يسبب تضاربًا، مثل أن تكون الحالة `active` بينما `used_at` يحتوي وقتًا.

## الملفات التي تخص هذه المرحلة

| الملف | مسؤوليته |
|---|---|
| `backend/app/database.py` | إنشاء محرك SQLAlchemy وجلسات قاعدة البيانات |
| `backend/app/models.py` | تعريف جدول `secrets` فقط |
| `backend/app/config.py` | قراءة عنوان قاعدة البيانات من إعدادات البيئة لاحقًا |
| `backend/tests/test_database.py` | اختبار النموذج باستخدام SQLite محلية مؤقتة |

## الاختبار

يستخدم الاختبار قاعدة SQLite مؤقتة داخل الاختبار فقط. الهدف ليس تغيير قاعدة بيانات المشروع الحقيقية، بل إثبات أن جدول الأسرار يُنشأ بالحقول الصحيحة وأنه لا يحتوي على `plaintext` أو `encryption_key`.

## ما لا يدخل في هذه المرحلة

لا يوجد AES-GCM، ولا مسارات FastAPI لإنشاء سر، ولا رابط، ولا Reveal، ولا اتصال فعلي بقاعدة بيانات الإنتاج. هذه الأشياء تأتي في مراحل مستقلة حتى يبقى المشروع مفهومًا وسهل الاختبار.

## معيار القبول

تكتمل المرحلة عندما ينجح اختبار Python في إنشاء جدول `secrets` وحفظ سجل تجريبي فيه، مع التأكد أن الحقول الممنوعة غير موجودة.

## نتيجة التنفيذ

تم إنشاء نموذج `Secret` واتصال SQLAlchemy القابل للاستخدام مع SQLite في الاختبارات ومع MySQL/TiDB لاحقًا. نجحت اختبارات Python وعددها اثنان: اختبار بيئة FastAPI واختبار جدول `secrets` وحقوله.

> لم يتم إنشاء قاعدة بيانات إنتاجية، ولم يتم تنفيذ تشفير أو API أو رابط مشاركة في هذه المرحلة. هذا مقصود حتى يبقى كل جزء منفصلًا وسهل الفهم.
