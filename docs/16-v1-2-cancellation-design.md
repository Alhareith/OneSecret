# V1.2 — تصميم إلغاء الرابط

## الهدف والحدود

يضيف V1.2 قدرة المرسل على تعطيل رابط رسالة أُنشئت بالفعل إذا أُرسل إلى جهة خطأ أو اشتبه في تسربه. الإلغاء لا يضيف حسابات أو جلسات أو سجلًا للمرسل؛ يظل إثبات التحكم هو **رمز إلغاء مستقل**.

لا يغير هذا الإصدار تشفير AES-256-GCM أو مدة الرابط أو العرض المتكرر أو الإتلاف بعد أول فتح أو Secret Code. ولا يمنع نسخ المحتوى أو تصوير الشاشة إذا كان المستلم قد كشف الرسالة قبل تنفيذ الإلغاء.

## عقد الأمان

| العنصر | القرار | السبب |
|---|---|---|
| توليد الرمز | يولد الخادم 32 بايت عشوائية تشفيريًا بصيغة URL-safe | الرمز عالي العشوائية ولا يعتمد على اختيار المستخدم |
| وقت الظهور | يعود في استجابة الإنشاء فقط ويعرض للمرسل في بطاقة النجاح الحالية | لا توجد واجهة استرجاع أو مسار يعيد الرمز لاحقًا |
| التخزين | يحفظ salt عشوائي واشتقاق `scrypt` فقط، ولا يحفظ الرمز الأصلي | تسريب قاعدة البيانات لا يعطي الرمز القابل للاستخدام مباشرة [1] |
| النقل | يرسل الرمز في جسم `POST` إلى مسار الإلغاء | لا يدخل URL أو سجل الوصول أو history [2] |
| الاستجابة الخاطئة | الرمز الخاطئ أو الرابط المفقود أو المنتهي أو الملغى يعيد حالة عامة واحدة `410` | لا يسمح بالاستدلال على حالة الرابط أو صحة الرمز [3] |
| الإلغاء الناجح | تحديث ذري يثبت `cancelled_at` ويمسح ciphertext وnonce ومواد Secret Code ورمز الإلغاء | بعد نجاح الإلغاء لا تبقى بيانات قابلة للكشف من قاعدة البيانات |
| السباق | يحدد التحديث الذري لحظة الإلغاء؛ الكشف الذي سبق التحديث قد ينجح، وأي كشف يبدأ بعده يرى حالة عامة غير متاحة | لا يمكن إلغاء محتوى عاد فعليًا قبل نجاح طلب الإلغاء |

> **معنى «فوري»:** عند عودة نجاح الإلغاء، لا تستطيع أي عملية كشف جديدة قراءة المحتوى. لا يمكن للنظام إزالة نص وصل إلى جهاز مستلم قبل نجاح الإلغاء.

## عقود API

### إنشاء الرسالة

يبقى طلب `POST /api/secrets` كما هو. يضيف الرد حقلًا واحدًا:

```json
{
  "id": "<48-hex-id>",
  "expires_at": "2026-08-27T12:00:00Z",
  "status": "active",
  "cancel_code": "<one-time sender-only value>"
}
```

لا يعاد `cancel_code` من status أو reveal أو أي endpoint لاحق. ولأن الرد يحتوي رمزًا حساسًا، يحمل مسار الإنشاء أيضًا `Cache-Control: no-store`.

### إلغاء الرابط

```text
POST /api/secrets/{secret_id}/cancel
Content-Type: application/json

{ "cancel_code": "<sender-only value>" }
```

| الحالة الداخلية | الرد الخارجي |
|---|---|
| رمز صحيح ورسالة نشطة | `200` مع `{ "id": "…", "status": "cancelled" }` |
| رمز خاطئ، رابط مفقود، رابط منتهٍ، رابط ملغى أو رسالة استُهلكت | `410` مع `Secret is unavailable` |
| تجاوز الحد | `429` مع `Retry-After` ورسالة انتظار عامة |
| جسم غير صالح | `422` برسالة تحقق عامة بلا عكس للرمز |

تستمر صفحة status في استخدام الحالات العامة الحالية. داخليًا توجد حالة `cancelled`، لكنها لا تعرض للمستلم؛ يعامل الرابط الملغى كغير متاح.

## الحد التشغيلي والسجل

يحصل مسار الإلغاء على حدين متكاملين: حد عام `60` طلبًا في الدقيقة لكل مصدر، ثم حد `5` محاولات رمز خاطئ خلال 10 دقائق لكل مصدر ولكل رابط. تستعمل مفاتيح محدد الطلبات بصمات HMAC الداخلية الموجودة في V1.1، فلا يحتفظ المحدد بمعرّف الرابط أو المصدر في صورة خام. تسجل حالة تجاوز الحد باسم العملية فقط، ولا تسجل الرمز أو الرابط أو النص.

هذا المحدد داخل عملية FastAPI واحدة؛ عند تشغيل عدة نسخ يظل الانتقال إلى مخزن مركزي مثل Redis قرارًا تشغيليًا لاحقًا، ولا يفترض هذا التصميم خلاف ذلك.

## تجربة المرسل

بعد إنشاء الرسالة، تظهر بطاقة النجاح الحالية مع رابط المشاركة، ويضاف إليها قسم قصير مستقل لرمز الإلغاء مع زر نسخ. النص يوضح أن الرمز **يظهر مرة واحدة فقط** وأنه لا يرسل مع الرابط. يوجد مسار `/cancel` خفيف يستطيع فيه المرسل إدخال رابط الرسالة أو معرّفها ورمز الإلغاء لاحقًا. تستخرج الواجهة المعرّف محليًا من الرابط، ثم ترسل المعرّف إلى مسار المشروع والرمز في جسم `POST` فقط.

لا تتغير صفحة المستلم. عند فتح رابط ملغى تعرض الحالة العامة المستخدمة أصلًا للرابط غير المتاح.

## خطة الاختبار

| الطبقة | حالات القبول |
|---|---|
| وحدة الخدمة | عدم تخزين رمز الإلغاء الأصلي، رفض الرمز الخاطئ، مسح البيانات عند النجاح، وذَرّية إلغاءين متزامنين |
| API | عودة الرمز مرة واحدة مع الإنشاء، نجاح الإلغاء الصحيح، عمومية الخطأ، عدم كشف حالة الرابط، منع reveal وstatus التفصيلي بعد الإلغاء، و`no-store` و`429` |
| الواجهة | إظهار الرمز ونسخه مرة واحدة، تحليل رابط صالح أو معرّف صالح محليًا، رسالة نجاح، ورسائل عامة للخطأ والحظر باللغتين |
| الانحدار | العرض المتكرر، Secret Code، الإتلاف بعد أول فتح، والانتهاء تبقى سليمة |

## التنفيذ والنتيجة

نُفذ التصميم في V1.2. أضيفت الأعمدة `cancelled_at` و`cancel_code_salt` و`cancel_code_hash`، وجُعل `ciphertext` و`nonce` قابلين للمسح بعد الإلغاء. طُبق الترحيل على جدول الإنتاج القائم بعد قراءة مخططه أولًا والتحقق من الأعمدة الناتجة. الرسائل السابقة التي لا تحمل مواد رمز إلغاء تظل قابلة للتشغيل حتى انتهاء صلاحيتها، لكنها لا تكتسب رمز إلغاء بأثر رجعي.

يولد `POST /api/secrets` رمزًا عشوائيًا من 32 بايت لكل رسالة جديدة، ثم يعيده مرة واحدة في استجابة `201` مع `no-store`. يتحقق `POST /api/secrets/{id}/cancel` من الاشتقاق بتوقيت ثابت، ثم ينفذ تحديثًا ذريًا واحدًا. تغطي V1.2 حد الطلب العام، وحد رموز الإلغاء الخاطئة لكل مصدر ولكل رابط، ومسارات `200` و`410` و`429` والرؤوس وغياب الرمز عن السجل.

أثبت التحقق النهائي نجاح 81 اختبار `pytest` و4 اختبارات `Vitest` وفحص TypeScript وبناء Vite. فصل البناء صفحة الإلغاء في chunk مستقل بحجم 8.40 kB خامًا و1.97 kB مضغوطًا؛ لذلك لا تدخل صفحة الإلغاء في حزمة البداية. كما تحقق تشغيل HTTP ومتصفح معزول ببيانات اختبار من الإلغاء الخاطئ والصحيح، وتعطيل reveal، وإخفاء الحالة، والواجهة العربية والإنجليزية.
