# المرحلة 3: تشفير AES-GCM في Python

## هدف المرحلة

بناء دوال Python واضحة لتوليد مفتاح AES-256، وإنشاء `Nonce` جديد، وتشفير رسالة نصية، وفكها، ثم اختبار النجاح وحالات الفشل. لا يوجد في هذه المرحلة رابط أو API أو حفظ في قاعدة البيانات؛ فهذه الدوال ستُستخدم في المراحل التالية.

## كيف ترتبط هذه المرحلة بالمقرر؟

ملف `Lab1 IT.pdf` يضع **AES Cipher** ضمن خوارزميات المقرر. أما المرجع التفصيلي المتوفر للمختبر، وهو دليل Vigenère، فيعلم طريقة بناء البرنامج: نحدد فكرة الخوارزمية، نكتب دالة مساعدة، نكتب دالة تشفير، نكتب دالة فك تشفير، ثم نختبر مثال نجاح وأخطاء متوقعة. سنحافظ على هذا **المنطق التعليمي** نفسه، لكن لا ننسخ معادلة Vigenère؛ لأن AES خوارزمية كتلية حديثة وتختلف رياضيًا عنها.

| في دليل المقرر | المقابل في OneSecret |
|---|---|
| `MakeKey` | `generate_key` للتحضير للمفتاح الصحيح |
| `Encryption(text, key)` | `encrypt_text(text, key, nonce)` |
| `Decryption(text, key)` | `decrypt_text(ciphertext, key, nonce)` |
| اختبار `ATTACK → LXFOPV → ATTACK` | اختبار `plaintext → ciphertext → plaintext` |
| مراجعة الأخطاء الشائعة | اختبار مفتاح خاطئ وNonce خاطئ وciphertext معدل |

## لماذا نستخدم AES-GCM وليس AES وحده؟

AES هو الخوارزمية الموجودة في قائمة المقرر. أما GCM فهو **نمط تشغيل** لـ AES. نستخدمه لأن الناتج لا يخفي النص فقط، بل يتحقق كذلك من عدم تعديل البيانات. لذلك إذا تغير ciphertext أو استُخدم مفتاح أو Nonce خاطئ، يفشل فك التشفير بدل إظهار نص غير موثوق [1].

## كلمات يجب فهمها

| الكلمة | معناها بالبلدي | وظيفتها |
|---|---|---|
| المفتاح `Key` | كلمة سر تقنية عشوائية طويلة، وليست كلمة يكتبها المستخدم | من يملكها يستطيع التشفير وفك التشفير |
| AES-256 | AES بمفتاح طوله 256 بت، أي 32 بايت | مستوى المفتاح الذي سنستخدمه |
| `Nonce` | رقم عشوائي جديد لكل عملية تشفير | يمنع تكرار نفس النتيجة مع المفتاح نفسه |
| `ciphertext` | النص بعد تحويله إلى بايتات غير مفهومة | هذا ما سيُحفظ في قاعدة البيانات |
| `InvalidTag` | خطأ سلامة من مكتبة التشفير | يظهر عندما تتغير البيانات أو يكون المفتاح أو Nonce غير صحيح |

## خطة الخطوات الصغيرة

### الخطوة 3.1: المفتاح

ننشئ `generate_key` لإنتاج مفتاح AES-256 عشوائي بطول 32 بايت، و`validate_key` لرفض المفتاح ذي الطول الخاطئ.

**اختبارات القبول:** مفتاح صحيح بطول 32 بايت؛ مفتاحان مولدان مختلفان؛ رفض مفتاح ناقص أو قيمة ليست `bytes`.

### الخطوة 3.2: Nonce

ننشئ `generate_nonce` لإنتاج قيمة عشوائية بطول 12 بايت لكل عملية تشفير.

**اختبارات القبول:** Nonce صحيح بطول 12 بايت؛ عينات جديدة مختلفة؛ رفض Nonce غير صالح قبل فك التشفير.

## سجل التنفيذ

### الخطوة 3.1 مكتملة: المفتاح

تمت إضافة دالتين في `backend/app/crypto.py`:

| الدالة | ماذا تعمل؟ |
|---|---|
| `generate_key()` | تنشئ مفتاح AES-256 عشوائيًا بطول 32 بايت |
| `validate_key(key)` | تتأكد أن القيمة بايتات وأن طولها 32 بايت قبل استخدامها |

الاختبارات شملت مفتاحًا صحيحًا، ومفتاحين مولدين للتأكد من اختلافهما، وأربعة أطوال خاطئة، وقيمة نصية بدل bytes. النتيجة: **7 اختبارات ناجحة**.

> لا يوجد Nonce أو ciphertext أو فك تشفير في هذه الخطوة. فصل هذه الأجزاء يجعل الكود مثل ترتيب مختبر Vigenère: نثبت الدالة المساعدة أولًا، ثم نبني فوقها.

### الخطوة 3.2 مكتملة: Nonce

تمت إضافة دالتين جديدتين:

| الدالة | ماذا تعمل؟ |
|---|---|
| `generate_nonce()` | تنشئ 12 بايت عشوائيًا جديدًا لكل عملية تشفير |
| `validate_nonce(nonce)` | ترفض أي قيمة ليست bytes أو لا يكون طولها 12 بايت |

اختبرنا 20 قيمة Nonce مولدة للتأكد من عدم التكرار داخل عينة الاختبار، واختبرنا الأطوال الخاطئة والقيمة النصية. النتيجة حتى الآن: **14 اختبارًا ناجحًا**.

> لا يعني نجاح 20 عينة أننا نستطيع «إثبات» عدم التكرار عالميًا؛ المقصود هو التحقق من أن دالة العشوائية تعمل كما نتوقع في الاختبار. قاعدة الاستخدام الفعلية هي: لا نعيد استخدام Nonce مع المفتاح نفسه.

### الخطوة 3.3 مكتملة: تشفير النص

تمت إضافة الدالة `encrypt_text(plaintext, key, nonce)`. تبدأ بالتحقق من نوع النص والمفتاح والـNonce، ثم تحول النص إلى `UTF-8` وتستدعي `AESGCM.encrypt`. الناتج هو bytes تحتوي ciphertext ووسم السلامة معًا؛ لذلك لا نحتاج إلى إضافة حقل مستقل للوسم في جدولنا.

اختبرنا نصًا عربيًا وإنجليزيًا، وتأكدنا أن الناتج bytes وغير فارغ ولا يساوي النص الأصلي، وأن تشفير النص نفسه مع Nonce مختلف يعطي ناتجًا مختلفًا. اختبرنا أيضًا نصًا غير صحيح، ومفتاحًا قصيرًا، وNonce قصيرًا. النتيجة حتى الآن: **18 اختبارًا ناجحًا**.

> في هذه الخطوة لا نستطيع إثبات أن ciphertext يعيد النص الأصلي بعد فك التشفير؛ هذا هو هدف الخطوة التالية فقط. فصل الاختبار بهذه الطريقة يمنعنا من خلط مسؤولية التشفير بمسؤولية الاسترجاع.

### الخطوة 3.4 مكتملة: فك التشفير والتحقق من السلامة

تمت إضافة الدالة `decrypt_text(ciphertext, key, nonce)`. تبدأ بفحص نوع ciphertext، ثم تستخدم المفتاح والـNonce في `AESGCM.decrypt`، وأخيرًا تحوّل bytes المسترجعة إلى نص `UTF-8`.

| الحالة | ماذا يجب أن يحصل؟ | نتيجة الاختبار |
|---|---|---|
| النص العربي والإنجليزي | يعود النص نفسه بعد تشفيره وفكه | ناجح |
| النص الفارغ | يعود نصًا فارغًا بشكل صحيح | ناجح |
| مفتاح خاطئ | ترفع المكتبة `InvalidTag` | ناجح |
| Nonce خاطئ | ترفع المكتبة `InvalidTag` | ناجح |
| ciphertext معدل | ترفع المكتبة `InvalidTag` | ناجح |
| ciphertext ليس bytes | ترفع دالتنا خطأ نوع واضح | ناجح |
| بيانات مفكوكة غير UTF-8 | ترفع دالتنا خطأ واضح | ناجح |

النتيجة النهائية لملف التشفير: **27 اختبارًا ناجحًا**. لاحقًا ستلتقط طبقة FastAPI خطأ `InvalidTag` وتعرض للمستخدم رسالة عامة، بدل أن تخبره هل المفتاح أو Nonce أو ciphertext هو الذي كان خاطئًا.

## الخلاصة التي تناقش بها المدرس

«اتبعت تسلسل المختبر: دالة تحضير للمفتاح، ثم Nonce، ثم دالة تشفير، ثم دالة فك تشفير، ثم اختبارات نجاح وفشل. AES موجودة في قائمة المقرر، لكن AES-GCM غير مشروحة تفصيليًا في الملفات المتاحة؛ لذلك استخدمت مكتبة Python القياسية `cryptography` لتنفيذ AES بصورة صحيحة، وأضفت GCM للتحقق من عدم تعديل الرسالة. لا كتبت AES من الصفر ولا خلطت التشفير بواجهة الموقع أو بقاعدة البيانات.»

### الخطوة 3.3: التشفير

ننشئ `encrypt_text`. تستقبل نصًا ومفتاحًا وNonce، ثم تحول النص إلى UTF-8 وتعيد ciphertext من AES-GCM.

**اختبارات القبول:** ciphertext لا يساوي النص الأصلي؛ لا يكون فارغًا؛ تشفير النص نفسه مع Nonce مختلف يعطي ciphertext مختلفًا.

### الخطوة 3.4: فك التشفير والتحقق

ننشئ `decrypt_text`. تستقبل ciphertext ومفتاحًا وNonce، ثم تعيد النص الأصلي فقط إذا كانت البيانات سليمة.

**اختبارات القبول:** استعادة النص العربي والإنجليزي الصحيح؛ رفض مفتاح خاطئ؛ رفض Nonce خاطئ؛ رفض ciphertext المعدل؛ رفض bytes غير صالحة للـUTF-8 بعد تحقق التشفير.

## قاعدة أمان مهمة

لا نكتب خوارزمية AES من الصفر؛ هذا غير مطلوب في مختبرنا وقد يؤدي إلى أخطاء. نحن نناقش منطق AES كما في المقرر، ثم نستخدم تنفيذ مكتبة `cryptography` القياسي لتنفيذ AES-GCM بشكل صحيح [1].

## ما لا يدخل في المرحلة

لن نقرأ مفتاح الإنتاج من البيئة الآن، ولن نحفظ ciphertext في الجدول، ولن نبني API أو رابط Reveal. هدف هذه المرحلة هو دوال تشفير مستقلة ومختبرة فقط.

## أداة توليد مفتاح محلي

يوجد الملف `backend/generate_key.py`. لا يحفظ مفتاحًا؛ بل يولد مفتاحًا جديدًا ويطبعه مرة واحدة عند تشغيله:

```bash
cd backend
python3 generate_key.py
```

انسخ الناتج مباشرة إلى الحقل الآمن `ONESECRET_ENCRYPTION_KEY`. لا تضف الناتج إلى Git أو ملف كود أو رسالة محادثة.

تم تشغيل الأداة والتحقق من ناتجها من دون عرضه؛ الناتج يفك إلى **32 بايت**، وهو الطول المطلوب لمفتاح AES-256.

> تم توليد مفتاح جديد والتحقق من صلاحيته. لا يمكن حفظه في الكود أو عرضه في المحادثة؛ يجب وضعه عبر حقل إعدادات المشروع الآمن فقط.

## إدارة المفتاح داخل الخادم

خادم Python يقرأ `ONESECRET_ENCRYPTION_KEY` من البيئة باستخدام `load_encryption_key()` في `backend/app/config.py`. الدالة تفك Base64 وتتحقق أن الناتج 32 بايت، ثم تعيد bytes للمكوّن الذي يحتاج التشفير فقط.

| ممنوع | السبب |
|---|---|
| وضع المفتاح داخل `crypto.py` أو `main.py` | سيظهر مع الكود وقد يُرفع إلى Git |
| حفظ المفتاح في جدول `secrets` | يجعل الوصول إلى القاعدة كافيًا لفك كل الرسائل |
| كتابة المفتاح في السجلات أو رسائل الخطأ | قد يظهر في أدوات المراقبة أو التقارير |
| إرساله إلى React | الواجهة لا تحتاجه في نموذج التشفير المعتمد داخل Python |

اختبرنا الدالة بمفتاح صحيح، وقيمة مفقودة، وقيمة ليست Base64، وقيمة Base64 بطول خاطئ: **4 اختبارات ناجحة**.
