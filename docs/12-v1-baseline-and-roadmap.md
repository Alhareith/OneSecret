# اعتماد OneSecret V1 وخارطة التطوير

## القرار المعتمد

اعتُمدت النسخة الحالية كـ **OneSecret V1**، أي النسخة الأولية التي تثبت أن الفكرة تعمل فعليًا: المرسل يكتب نصًا، يحدد مدة، يحصل على رابط، ثم يقرأ المستلم الرسالة ضمن القواعد التي اختارها المرسل. لا تدخل أي ميزة جديدة إلى V1 من دون قرار مستقل واختبار واضح.

> **قاعدة الطريق:** لا نضيف ميزة لأنها تبدو جميلة. نضيفها فقط إذا حلت مشكلة حقيقية، ولم تضعف الأمان، وكانت مناسبة لحجم المرحلة.

## ما يقدمه V1 الآن

| المجال | ما هو موجود ومُعتمد |
|---|---|
| الرسالة | رسالة نصية فقط، حتى 10,000 حرف |
| الحماية أثناء التخزين | AES-256-GCM داخل Python؛ لا يُحفظ `plaintext` في قاعدة البيانات |
| الرابط | معرّف عشوائي طويل داخل `/s/{id}`؛ يعرض الرابط المختصر في الواجهة فقط |
| الصلاحية | الرابط يعمل عدة مرات حتى `expires_at`، وخيارات المدة من دقيقة إلى 24 ساعة |
| الإتلاف | «إتلاف بعد أول فتح» خيار اختياري، ويُنفذ ذريًا في الخادم |
| Secret Code | اختياري؛ يمر في جسم طلب POST ولا يوجد في الرابط أو التخزين كنص أصلي؛ يحفظ salt واشتقاق scrypt فقط |
| تجربة الهاتف | صفحة عربية RTL وإنجليزية LTR، مشاركة النظام الأصلية على الأجهزة الداعمة، وزر نسخ مستقل |
| الجودة المثبتة | 81 اختبار Python، و4 اختبارات Vitest، وفحص TypeScript وبناء Vite؛ تحصين V1.1 وإلغاء V1.2 موثقان ومتحقق منهما |

## حدود V1 المقصودة

هذه الحدود ليست نواقص يجب إصلاحها فورًا؛ هي حماية من تضخيم مشروع المقرر. لا توجد حسابات، أو فرق عمل، أو ملفات، أو دردشة، أو تحرير للرسالة، أو سجل شخصي للمرسل، أو تنبيهات، أو تشفير طرفي إلى طرفي. كذلك لا يستطيع الموقع منع تصوير الشاشة أو نسخ المحتوى بعد عرضه.

V1 هو **نموذج خادم موثوق**: يرى الخادم النص لحظة التشفير وفك التشفير، لكنه لا يخزن النص واضحًا في قاعدة البيانات. لا يجب تسويق هذه النسخة على أنها تشفير طرفي إلى طرفي.

## كيف نختار أي تطوير جديد؟

كل فكرة تمر بخمسة أسئلة قبل كتابة الكود. إن لم يكن جوابها واضحًا، تؤجل الفكرة.

| السؤال | المقصود بالبلدي |
|---|---|
| ما المشكلة؟ | من سيتأذى أو يتعطل الآن، وكيف تحلها الميزة؟ |
| ما أثرها الأمني؟ | هل تضيف سرًا جديدًا، أو طريقة جديدة لتخمين الرابط، أو سجلًا حساسًا؟ |
| ما أصغر حل؟ | ما أقل عدد من الشاشات والحقول والجداول الذي يحل المشكلة؟ |
| كيف نختبرها؟ | ما الاختبار الذي يثبت النجاح، وما الاختبار الذي يثبت عدم تسرب شيء؟ |
| هل تناسب المرحلة؟ | هل تخدم V1 فعلًا أم تحول المشروع إلى منصة كبيرة؟ |

## خارطة الطريق المعتمدة

### V1.1 — التحصين التشغيلي: مكتملة

الهدف ليس إضافة واجهة جديدة، بل منع إساءة استخدام النظام. نُفذ حد للطلبات على إنشاء الرسالة وعلى محاولات Reveal وSecret Code، مع استجابة `429` عامة عند تجاوز الحد. لا يسجل التطبيق الرسالة أو Secret Code أو الرابط الكامل في سجل الحماية؛ يكفي حدث مختصر مثل نوع العملية والنتيجة ووقت الحدث. تظل أخطاء المستخدم عامة، وتظهر للواجهة رسالة انتظار محلية عند الحظر بدل وصفه بكود خاطئ.

أضيفت أيضًا رؤوس حماية للصفحات والاستجابات الحساسة، وأهمها `Cache-Control: no-store` حيث يعاد النص أو يعالج رابط محدد، و`X-Content-Type-Options: nosniff`، وحماية الإطارات. بقيت `web-share` مسموحة، لذلك لا ينكسر زر مشاركة الهاتف. تحققت الاختبارات من الاستجابات الناجحة و`401` و`410` و`429`، ومن سجل تشغيل لا يحوي النص أو Secret Code الاختباري. التقرير التفصيلي وحد التشغيل موجود في [`docs/13-v1-1-hardening-design.md`](./13-v1-1-hardening-design.md). توصي OWASP بعدم وضع الأسرار في URL، وبالاستجابات العامة، وبـ`no-store` للمحتوى الحساس، وبحدود الطلبات للخدمات العامة [1]. كما أن NIST يركز على تقييد محاولات التحقق من الأسرار لتقليل التخمين [2].

**معيار القبول:** محاولات Secret Code الخاطئة المتتالية تتوقف مؤقتًا، ولا تظهر في السجلات أي رسالة أو Code، ولا يحتفظ المتصفح باستجابة Reveal الحساسة في ذاكرة التخزين المؤقت.

### V1.2 — إلغاء الرابط من المرسل: مكتملة

المشكلة: قد يرسل المرسل الرابط إلى شخص خطأ أو يشعر أن الرابط تسرب. نُفذ الحل الأصغر: **رمز إلغاء منفصل** يظهر مرة واحدة للمرسل عند الإنشاء، ويُحفظ الخادم منه salt واشتقاق `scrypt` فقط. يستطيع المرسل لاحقًا إدخال الرابط أو المعرّف والرمز في صفحة `/cancel`؛ تستخرج الواجهة المعرّف محليًا ويرسل الرمز في جسم `POST` فقط، ولا تدخل قيمته URL أو السجل أو التخزين كنص أصلي.

ينفذ الإلغاء تحديثًا ذريًا يثبت `cancelled_at` ويمسح ciphertext وnonce ومواد Secret Code ورمز الإلغاء. بعد النجاح يرد مسار الكشف بحالة عامة `410`، وتعيد حالة الرابط `missing` بلا وقت انتهاء، فلا تكشف للمستلم أن المرسل اختار الإلغاء. لا يستطيع الإلغاء استرجاع نص سبق كشفه أو نسخة حفظها مستلم قبل نجاح الإلغاء. التقرير المفصل موجود في [`docs/16-v1-2-cancellation-design.md`](./16-v1-2-cancellation-design.md).

**معيار القبول المتحقق:** رمز الإلغاء الصحيح يعطل الرابط؛ الرمز الخاطئ لا يكشف حالته ولا يغيرها؛ تمسح المواد القابلة للكشف؛ وتغطي اختبارات الخدمة وAPI التزامن والحدود والرؤوس.

### V1.3 — مشاركة الصور المؤقتة

هذه المرحلة **مستقلة** وتبدأ فقط بعد نجاح V1.1 وV1.2. لا تتحول إلى «رفع أي ملف». نطاقها الأول هو: **صورة واحدة فقط** لكل رسالة، بصيغ JPEG أو PNG أو WebP، وحد حجم صغير يحدد قبل التنفيذ، مع استخدام نفس الرابط والمدة وSecret Code والإتلاف التي اختارها المرسل للنص.

تُرفع الصورة إلى تخزين ملفات منفصل بدل قاعدة بيانات `secrets`. يتحقق الخادم من الحجم ونوع الملف وتوقيعه الفعلي، يولد اسمًا عشوائيًا لا يعتمد على اسم المستخدم، ثم يعيد ترميز الصورة ويزيل بيانات EXIF قبل حفظ النسخة. لا تحل تسمية `Content-Type` محل التحقق الحقيقي، ولا يسمح بـSVG أو GIF المتحرك أو PDF أو ZIP أو فيديو في هذه المرحلة. توصي OWASP بقائمة أنواع مسموحة، وحدود للحجم، وفحص النوع والتوقيع، وتخزين معزول، وإعادة ترميز الصور ضمن دفاع متعدد الطبقات [5].

**معيار القبول:** لا تقبل الواجهة إلا صورة واحدة ضمن الأنواع والحجم المعتمدين؛ لا يظهر اسم الملف الأصلي أو بيانات EXIF؛ لا يمكن تنزيل أو عرض الصورة بعد الانتهاء أو الإلغاء أو الإتلاف؛ وتغطي الاختبارات النوع والحجم والملف التالف وانتهاء الصلاحية.

### V1.4 — سياسات وصول واضحة

هذه المرحلة تضيف **حد المشاهدات** كخيار مستقل، مثل «حتى 3 فتحات»، بدل ربطه بالانتهاء أو بالإتلاف. يحتاج ذلك عدادًا وتحديثًا ذريًا حتى لا يتجاوز طلبان متزامنان الحد. الفكرة مفيدة عندما يريد المرسل السماح بالعودة إلى الرسالة، لكن ليس بلا نهاية. منتجات مشاركة الأسرار تفصل عادة بين انتهاء الوصول والحذف وحد المشاهدات، وهو فصل سليم مفهوميًا [4].

يمكن في نهاية هذه المرحلة إضافة رسالة اختيارية للمرسل تحدد بوضوح أن الرابط وSecret Code يجب مشاركتهما عبر قناتين مختلفتين. لا يلزم أن تكون هذه نافذة مزعجة؛ يكفي نص قصير قرب الحقل. هذا يتفق مع توجيهات خدمة أسرار قائمة باستخدام أقصر مدة عملية، وفصل القناة التي يحمل الرابط عن القناة التي تحمل passphrase [3].

### V1.5 — النظافة التشغيلية

بعد تثبيت استخدام واقعي، تضاف عملية دورية تحذف `ciphertext` و`nonce` وسجل السر بعد مدة احتفاظ مكتوبة ومحددة، مثل 24 ساعة بعد الانتهاء أو الإتلاف. لا يكفي أن يصبح الرابط غير متاح؛ الحذف يقلل ما يبقى في قاعدة البيانات. يجب أن تكون هذه العملية قابلة للمراقبة، وأن يسبق تنفيذها قرار واضح لمدة الاحتفاظ، لأنها لا يمكن التراجع عنها. لا تبدأ هذه المرحلة قبل تحديد طريقة تشغيل موثوقة للمهام الدورية.

## ما لا نفعله الآن

| الفكرة | لماذا تؤجل؟ |
|---|---|
| PDF والفيديو والملفات العامة | توسع المخاطر والأحجام وأنواع المعالجة كثيرًا؛ لا تدخل مع مرحلة الصور الأولى |
| حسابات ولوحة مستخدم | تضيف مصادقة وجلسات واسترداد حساب وصلاحيات وخصوصية بيانات؛ لا تحل مشكلة V1 العاجلة |
| إشعارات بريد أو واتساب | تحتاج جهات خارجية وبيانات اتصال وموافقات، وقد تجعل الخدمة أكثر تعقيدًا من فائدة المقرر |
| تشفير طرفي إلى طرفي | ليس تبديل مكتبة؛ يحتاج أن يتغير من يملك المفتاح، واسترداد الرابط، وطريقة حماية Secret Code بالكامل |
| ذكاء اصطناعي أو Blockchain | لا يحلان مشكلة إرسال السر، ويشتتان عن التشفير والمدة والتحكم في الوصول |

## الالتزام بالخطة

بعد اكتمال **V1.1 التحصين التشغيلي** و**V1.2 إلغاء الرابط من المرسل**، تصبح **V1.3 مشاركة الصور المؤقتة** المرحلة التالية المعتمدة. لا تبدأ مرحلة الصور قبل مراجعة نطاقها التفصيلي. وإذا ظهر طلب جديد، نقارنه بهذه الخارطة بدل إضافته فورًا؛ فإن خدم مشكلة أعلى أولوية نعيد ترتيب الخطة علنًا، وإلا يوثق في قائمة «مؤجل» فقط.
