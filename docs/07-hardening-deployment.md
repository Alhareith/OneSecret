# المرحلة 7: التقوية وتجهيز التشغيل الموحّد

## الهدف

تحويل المشروع من معاينة تطوير تعتمد على خدمتين منفصلتين إلى تشغيل واضح: خادم FastAPI واحد يعرض API وواجهة React المبنية، مع بقاء التشفير والمفتاح داخل Python فقط.

## كلمات صغيرة مهمة

| الكلمة | معناها البسيط | أثرها هنا |
|---|---|---|
| **Fail closed** | عند غياب الإعداد الأمني، يتوقف التطبيق بدل أن يكمل بشكل ضعيف | خادم الإنتاج يرفض البدء إذا لم توجد قاعدة البيانات أو مفتاح AES |
| **SPA fallback** | أي رابط واجهة يعيد ملف React الأساسي، ثم React يختار الصفحة داخله | يفتح `/s/{id}` مباشرة بدل أن يعطي 404 |
| **بيانات تالفة** | `ciphertext` أو `nonce` تغير أو لم يعد صالحًا للفك | يحصل المستلم على رسالة عامة فقط، لا تفاصيل عن التشفير |

## تعديلات المرحلة

| القرار | السبب |
|---|---|
| رفض معرّف رابط غير عشوائي أو غير صحيح الطول | تقليل الطلبات غير المنطقية قبل قاعدة البيانات |
| رفض وقت بلا منطقة زمنية أو مدة تتجاوز 24 ساعة | توحيد معنى الوقت مع خيارات الواجهة |
| تحويل تلف AES-GCM إلى رسالة عامة | منع كشف تفاصيل البنية الداخلية |
| إرجاع `index.html` لمسار `/s/{id}` | كي يفتح رابط المستلم مباشرة بعد النشر |
| Dockerfile يجمع Node وPython | لأن الواجهة والخادم يحتاجان تشغيلًا واحدًا في الإنتاج |

## التقوية الأمنية

تتحقق API الآن من أن معرف الرابط يتكون من **48 رمزًا سداسيًا عشريًا**، وهو الشكل الذي تولده الواجهة من 24 بايت عشوائية. كما ترفض وقت انتهاء بلا منطقة زمنية، أو وقتًا يتجاوز 24 ساعة، وهي الخيارات المتاحة للمستخدم في الواجهة. هذه ليست «حماية تشفير» وحدها، لكنها تمنع بيانات عبثية من الوصول إلى قاعدة البيانات.

عند كشف السر، أي فشل في التحقق من AES-GCM أو Base64 أو تحويل النص يتحول إلى `410 Secret is unavailable`. هذا مهم لأن مكتبة `cryptography` تثير `InvalidTag` عندما تكون البيانات أو المفتاح أو nonce غير صحيحة؛ لا ينبغي أن تصل هذه المعلومة الداخلية إلى المستلم [1].

## اختبار المتصفح على الخدمة الموحّدة

عند تنفيذ هذه المرحلة، أُدخلت رسالة اختبار غير حساسة عبر واجهة React التي قدّمها FastAPI نفسه، فظهر رابط `/s/{id}`. أثبت الاختبار وقتها أن فتح `/s/{id}` في تبويب جديد يعمل عبر مسار SPA والاتصال بـ API من دون الاعتماد على proxy التطوير.

## نتائج الاختبار

| الفحص | النتيجة |
|---|---|
| اختبارات Python | `47 passed`، وتشمل اختبار ciphertext تالفًا وقواعد إدخال جديدة |
| فحص TypeScript | ناجح عبر `pnpm check` |
| بناء React | ناجح عبر `pnpm build` |
| فحص تدفق موحّد عبر HTTP (وقت المرحلة) | إنشاء السر، فتح `/s/{id}`، Reveal واحد، ورفض Reveal الثاني: ناجح |
| اختبار المتصفح (وقت المرحلة) | إنشاء رسالة اختبار، فتح الرابط مباشرة، ثم إظهار النص: ناجح |
| إعادة فتح الرابط في المتصفح (وقت المرحلة) | ظهرت حالة `used` ولم يظهر النص: ناجح |
| غياب إعداد الإنتاج | الخادم رفض البدء بدل العمل من دون قاعدة بيانات أو مفتاح: ناجح |

> **تحديث الواجهة الحالي:** لم تعد صفحة المستلم تعرض زر Reveal. عند فتح رابط صالح، ترسل الواجهة طلب Reveal واحدًا تلقائيًا وتعرض النص مباشرة؛ يوثق `docs/06-reveal-interface.md` و`docs/09-ui-redesign.md` السلوك الحالي وفحوصه.

## Dockerfile والنشر

يوجد الآن `Dockerfile` في جذر المشروع لأنه مطلوب لإتاحة Python داخل صورة الموقع. يبني Dockerfile واجهة React في `frontend/dist`، يثبت متطلبات Python داخل بيئة مستقلة، ثم يشغل Uvicorn على قيمة `PORT` التي توفرها منصة الاستضافة. تخدم FastAPI ملفات React الثابتة وتعيد `index.html` لمسارات الواجهة؛ هذا يتبع مبدأ الملفات الثابتة وواجهات العميل الموثق في FastAPI [2].

> **مهم:** لم يُنشر الموقع علنًا في هذه المرحلة، ولم يتم ادعاء أن `ONESECRET_ENCRYPTION_KEY` الحقيقي موجود في بيئة الإنتاج. قبل النشر يجب التأكد من إدخال مفتاح Base64 حقيقي بطول 32 بايت في إعداد البيئة الآمن، من دون وضعه في الكود أو Git أو هذه الوثيقة.

لا يمكن اختبار بناء Docker محليًا في هذه البيئة، لذلك اختُبرت الأجزاء التي سينفذها: بناء React، تشغيل FastAPI الموحد، تدفق API، وفشل التشغيل عند غياب الإعداد. يبقى اختبار بناء الصورة الفعلي خطوة تتم عند إنشاء نقطة استعادة ثم اختيار النشر من واجهة المشروع.

## ما لا تغيره هذه المرحلة

هذه المرحلة لا تجعل النظام تشفيرًا طرفًا لطرف، ولا تمنع تصوير الشاشة، ولا تضيف حسابات أو PIN أو إلغاء الرابط. وظيفتها هي جعل الوظائف الموجودة تتصرف بأمان أوضح وتعمل من خدمة واحدة.
