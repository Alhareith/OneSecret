# المرحلة 11: الصلاحية، الإتلاف الاختياري، وSecret Code

## القرار المعتمد

تصبح مدة الرابط هي الحد الفعلي الافتراضي للوصول إلى الرسالة. يستطيع أي شخص يملك الرابط فتحها عدة مرات قبل `expires_at`، ثم يعيد الخادم حالة عامة ولا يكشف النص بعد الانتهاء.

يبقى الإتلاف بعد أول فتح خيارًا صريحًا فقط باسم `destroy_on_open`. إن لم يفعّله المرسل، لا يعدل كشف الرسالة `used_at`. وإن فعّله، يظل الاستهلاك الذري الحالي هو الحماية التي تمنع نجاح أكثر من كشف واحد متزامن.

## Secret Code

Secret Code اختياري. عند اختياره، لا تحفظ قاعدة البيانات الكود نفسه؛ تحفظ salt عشوائيًا واشتقاق `scrypt` منه فقط. لا يدخل الكود في الرابط أو استجابة API أو التوثيق التشغيلي أو السجلات. يرسل المتصفح الكود في جسم POST المشفر عبر HTTPS فقط عند طلب كشف الرسالة.

| الحالة | السلوك |
|---|---|
| رسالة عادية قبل الانتهاء | تظهر في كل فتح |
| رسالة عادية بعد الانتهاء | لا تظهر |
| رسالة بكود صحيح قبل الانتهاء | تظهر في كل فتح |
| رسالة بكود خاطئ أو مفقود | استجابة عامة 401، ولا يستهلك الرابط |
| إتلاف بعد أول فتح | نجاح واحد فقط؛ ثم تصبح الرسالة غير متاحة |

تستخدم الواجهة طلب كشف أولًا من دون كود. إذا كانت الرسالة محمية، تعرض حقل Secret Code فقط؛ لا تستخدم `status` كطلب إضافي. يرسل الإدخال الصحيح طلب كشف جديدًا، أما طلب StrictMode الأول فيبقى محميًا بالمخزن الحالي لعدم التكرار.

## معاينة التنفيذ الأولية

ظهرت صفحة الإنشاء بالعربية مع حقلي المدة والرسالة كما كانا، وأضافت قسمًا مطويًا باسم «خيارات إضافية» يحوي Secret Code وخيار الإتلاف. لا يلزم المستخدم العادي فتح القسم لإرسال رسالة قابلة للعرض حتى انتهاء مدتها.

أُنشئت رسالة عادية من الواجهة من دون Code أو إتلاف، ثم فُتح رابطها بنجاح وعُرض النص تلقائيًا. الخطوة التالية هي إعادة فتح الرابط نفسه للتأكد أن الفتح الأول لم يستهلكه.

فُتح الرابط نفسه مرة ثانية قبل انتهاء مدته وعرض النص مرة أخرى بنجاح. ثم جُعل الرابط منتهيًا في قاعدة الاختبار وأعيد فتحه؛ ظهرت حالة «هذا الرابط غير متاح» ولم يظهر النص. وهكذا صار انتهاء المدة هو الحد الفعلي للرسالة العادية.

أُنشئت رسالة جديدة مع Secret Code اختباري من واجهة الإنشاء. لم يظهر الكود في بطاقة الرابط أو رابط المشاركة؛ ظهر معرّف الرابط المعتاد فقط. سيُختبر الآن طلب الكود الخاطئ ثم الصحيح ثم إعادة الفتح.

عند فتح الرابط من دون Code، لم يظهر نص الرسالة؛ ظهرت بطاقة إدخال Secret Code فقط. أُدخل كود خاطئ لاختبار أن المحاولة غير الصحيحة لا تستهلك الرابط.

رفضت الواجهة الكود الخاطئ برسالة عامة من دون عرض النص. ثم أُدخل الكود الصحيح وظهرت الرسالة بنجاح؛ وهذا يثبت أن المحاولة الخاطئة لم تستهلك الرابط. سيُعاد فتح الرابط نفسه للتأكد من طلب الكود ونجاحه أكثر من مرة قبل انتهاء المدة.

أُعيد فتح الرابط المحمي بعد نجاح الفتح الأول، وطلب Secret Code من جديد ثم عرض الرسالة بالكود الصحيح للمرة الثانية. بهذا ثبت السلوك المتكرر للرسالة المحمية ما دامت الصلاحية قائمة.

بدأ اختبار خيار الإتلاف المنفصل من الواجهة: أُدخلت رسالة جديدة وترك Secret Code فارغًا، ثم سيُفعّل خيار «إتلاف بعد أول فتح» صراحة قبل إنشاء الرابط.

فُعّل الخيار وأنشئ رابط جديد. سيُفتح الرابط مرة واحدة ثم يُعاد فتحه لاختبار أن الإتلاف لم يعد السلوك الافتراضي، بل يعمل فقط لهذا الرابط الذي فعله المرسل.

أثناء الاختبار الأول للخيار، ظهر أن السجل المؤقت أنشئ بقيمة `destroy_on_open = 0`؛ لذلك لم يكن اختبارًا صحيحًا للإتلاف. سُجلت الملاحظة كخلل واجهة مستقل، وسيُتحقق من تمرير قيمة checkbox إلى طلب الإنشاء ثم يعاد الاختبار قبل اعتماد النتيجة.

أظهر فحص بيئة المعاينة أن نقر أداة الاختبار على checkbox لم يبدّل قيمته، بينما نقر DOM القياسي بدّله وفعّل حدث الواجهة. لذلك سيعاد اختبار المسار مع قيمة مؤكدة قبل الحكم على منطق الخادم.

أُنشئ رابط اختبار جديد بعد تأكيد قيمة checkbox، وتحققت قاعدة الاختبار من حفظ `destroy_on_open = 1` و`used_at = NULL` قبل أول فتح. هذا هو الرابط الذي سيستخدم للتحقق من الفتح الواحد الحقيقي.

عُرضت رسالة الإتلاف المؤكدة في الفتح الأول، ثم أعيد فتح الرابط نفسه وعادت حالة «هذا الرابط غير متاح» من دون النص. بذلك يعمل الإتلاف فقط عند اختيار المرسل له صراحةً، بينما تظل الرسائل الافتراضية ورسائل Secret Code قابلة للعرض حتى انتهاء المدة.

وتحققت صفحة الإنشاء بالإنجليزية واتجاه LTR: ظهرت `Optional Secret Code` و`Destroy after first open` والوصف المختصر لكل منهما بصورة متناسقة.
